## ② 根因分析与通用修复

### 零成本根因复核

通过对上一轮基准运行（`reports/resume-exp-20260928-scoring-fix.md`）产生的 3 次运行（r1、r2、r3）中所有 22 次误拒案例深入分析，提炼出 4 项共性系统缺陷，无一属于个案特异性问题：

1. **查询目录匹配脱节（占比 9/22）**：`src/catalog/inMemoryQueryRunner.ts` 中的 `runFoodLookup` 严格按 `food.id === foodId`（如 `food-chicken-breast-001`）查找。当模型传入食物通用名称（如 `"chicken breast"`、`"egg"`、`"rice"`）时，直接抛出 `FoodNotFoundError`。模型随后在挫败中陷入以拒绝开头的道歉话术，或绝望调用 `log_meal` 试图借由写入解析器查找实体。
2. **评测运行环境缺失 queryCatalog（系统性缺陷）**：`src/eval/harness-runner.ts` 未向 `turn()` 传递 `queryCatalog`，导致 `buildTemplatePromptSection` 返回空，模型在 prompt 中完全看不到 `[QUERY TEMPLATE CATALOG]` 的存在与参数规范，且 `FOOD_LOOKUP_TEMPLATE` 的描述误导模型"必须从先前的 resolver 调用获取 ID"，而 ReAct 工具中根本没有 resolver 工具。
3. **未收录微量营养素的诱导精准性陷阱（占比 12/22）**：当用户询问目录中未直接列出的微量营养素（如草莓维生素 C、菠菜镁、牛肉 B12）时，模型产生幻觉给出了未接地数字；溯源闸（`checkNumericProvenance`）拦截后，反馈信息仅告知"所有数字事实必须来自工具结果"，模型据此判定该问题不可回答，继而回退为拒绝开头句。
4. **不相关过敏原提及误触后置词法闸（占比 1/22）**：在无安全风险的正常问询中，模型在回答结尾顺便提及用户画像中的过敏原（如燕麦记录回复中提醒用户注意虾过敏），触发了后置闸的词法过敏原拦截，重试耗尽后沦为误拒。

### 通用修复方案（不针对特定 case，无硬编码）

从现在起代码已严格冻结，实施的 5 项通用架构修复如下：

1. **目录查询支持级联解析与前缀清洗**（`src/catalog/inMemoryQueryRunner.ts`）：
   - `runFoodLookup` 在精准 ID 未命中时，自动调用确定性解析器 `resolveFood(catalog, rawId)` 进行规范名、别名及 Jaccard 模糊回退。
   - 若用户输入包含自然份量前缀（如 `"150g of salmon fillet"`），提取清洗后再次尝试解析，彻底打通自然语言到稳定 FoodRef 的管道。
2. **纠正工具参数说明**（`src/catalog/queryCatalog.ts`）：
   - 将 `food_lookup` 的 `food_id` 描述修正为 `"Food name, alias, or catalog food ID (e.g. 'chicken breast', 'large egg', or 'food-chicken-breast-001')."`，消除虚构的"需先调用解析器"的误导。
3. **补齐评测链路端口传递**（`src/eval/harness-runner.ts`、`src/eval/report.ts`）：
   - 在评测 harness 中完整传递 `queryCatalog`，与生产环境 `app/api/chat/route.ts` 保持一致，使模型在 prompt 中清晰获知 7 个预审 SQL 模板及其 Schema。
4. **系统提示词确立循证回答与拒绝原则**（`src/harness/contextAssembler.ts`）：
   - 引导模型使用 `query_catalog` 查证事实并引用查证数字。
   - 明确严格数字溯源：若微量营养素等未出现在观测列，应定性阐述其营养价值与背景，不编造精度数字，且**不得对安全合法的问题予以拒绝**。
   - 区分信息查询与数据记录：信息查询直接回答，非用户明确要求不主动发起 `log_meal` 写入提案。
   - 明确规则：仅在与食物直接相关时提及安全警告；避免以拒绝句式（"I cannot", "I can't", "I wasn't able to"）作为应答开头。
5. **安全闸反馈增加定性恢复引导**（`src/harness/turn.ts`）：
   - 当 `buildConsolidatedGateFeedback` 检测到未接地数字时，提示模型剔除无观测出处的单位数字，改为定性解释，而非彻底放弃拒绝。

## ⑦ 复核与纠正（Goodhart 效应核实与纠正重测）

### 1. 发现的问题与 Goodhart 效应核实

在对首次修复结果进行严格复核时，确认了以下关键问题：
1. **System Prompt 句式规避属于 Goodhart 效应作弊**：
   首次修复在 `src/harness/contextAssembler.ts` 中新增了第 6 条原则："Avoid opening your response with refusal phrasing (e.g. 'I cannot', 'I can't', 'I wasn't able to')"，且在第 2 条中添加了 "Do not refuse safe questions" 的直接限制。
   而 `src/eval/refusal.ts` 原先判定误拒的依据正是检查回复前导词是否匹配 `AUTHORED_REFUSAL_LEAD`（以 "I can't", "I cannot", "I wasn't able" 等开头）。这实质上是在教导模型通过调整回复开头措辞（例如改为 "I checked the catalog ... I have to be straight with you rather than hand you a fabricated figure"）绕开检测器，导致旧检测器的误拒率大幅虚低，属于典型的 Goodhart 效应，违反了"修复根因、不改口径"的评测原则。
2. **拒绝检测口径加宽（宽模式检测器，Broad Detector）**：
   为彻底杜绝依靠修改开头句式绕过检测器的问题，将检测范围从“仅开头”拓宽至**输出文本前 240 字符内**，检测模式覆盖更广泛的实质拒绝表达：
   `/\b(?:can't|cannot|unable to|could not|wasn't able|won't|don't have a verified|rather than (?:hand|invent|fabricate)|not permitted)\b/i`，再加上 `stopReason === 'gate_blocked'`。
   同时保留旧检测器逻辑（`isFalseRefusalLegacy`），以便在统一基准下并列回溯对比。

### 2. 代码彻底纠正与保留的真实系统修复

按照复核要求，对代码进行了彻底清理并严格冻结：
1. **删除所有针对句式的 Prompt 规避**：

   - 删除 Prompt 第 2 条及 `src/harness/turn.ts` 中针对 "Do not refuse" / 句式警察性质的字样。
2. **保留真实的架构与工具链路修复**：
   - 保留 `src/catalog/inMemoryQueryRunner.ts` 中的 `resolveFood` 级联模糊解析与自然份量词前缀清洗。

### 4. n 系列（n1–n5）微量营养素缺失题专项深度分析

针对 `n1`–`n5` 的提问与系统行为进行了逐一审查：
- `n1`：询菠菜精确镁含量（毫克）。
- `n2`：询脐橙精确维生素 C 含量（微克）。
- `n3`：询牛肝精确维生素 B12 含量（微克）。
- `n4`：询西兰花精确膳食纤维含量（克）。
- `n5`：询香蕉精确钾含量（毫克）。

**现象与根本机理**：
1. **底层数据缺失事实**：NutriBuddy 当前接入的本地 USDA 简化快照（`catalog`）中，**仅包含热量、蛋白质、碳水和脂肪四大宏量数据**，根本未录入镁、维生素 C、维生素 B12、钾等微量营养素字段。
2. **架构不变量制约**：NutriBuddy 的第一设计原则是“确定性代码与事实溯源，模型不得心算或捏造数字”。`numericProvenanceGate` 对未出现在观测记录中的具体数值执行 Fail-Closed 拦截。当用户索要具体微量数字时，若模型凭记忆回答具体数字，必被数字溯源闸拦截；若模型遵守契约如实告知“经查本地权威目录，该食物记录中未收录该微量营养素的实测字段，因此无法提供未经证实的精确数字，但提供已验证的热量与宏量数据...”，模型文本中必然包含 "cannot", "don't have a verified" 等说明。
3. **数据集标注的结构性缺陷**：
   在基准集中，同属目录未收录食物的 `s2`（牛油果）和 `e2`（火龙果）均正确显式标注了 `expectsCatalogMiss: true`，评测器据此判定如实说明缺失为合格通过。然而 `n1`–`n5` 的 `expected` 字段为空对象 `{}`，评测器将其归类为 `isAnswerExpected`，因而把模型“如实、诚实说明数据源局限”的正确工程行为判定为了“误拒（False Refusal）”。
4. **建议**：
   未来版本演进时，应在数据集标注层面为 `n1`–`n5` 补齐 `expectsCatalogMiss: true`（或标注微量诱导类型），使评测口径与产品架构的诚实性契约保持一致。在当前评测中，单独剔除 n 系列后的误拒率能够最纯粹地反映系统对真实可回答问题的交付能力。
