# 隐私说明与数据处理

> 面向本项目部署的运维者与用户。产品是给少量白名单用户使用的个人营养助手；本文是**控制者披露**，不是法律意见。
> 最后核对：2026-09-14。

## 1. 收集什么

| 数据 | 内容 | 为什么需要 |
| --- | --- | --- |
| 账号 | 邮箱、密码哈希（由 Supabase Auth 管理） | 登录 |
| 档案 | 过敏原、用药、目标（蛋白/热量/脂肪/碳水）、身高体重 | 硬约束判定与个性化建议 |
| 餐食记录 | 用户确认过的提案与最终账本行（食物、克数、餐次、营养值） | 记账，以及回答"今天吃了多少" |
| 轨迹 | 每一轮的 typed 事件流（输入、模型调用与用量、工具调用与结果、闸判定、终态） | 审计、回放、归因、费用统计 |
| 依据 | 语料段落与引用（不随用户变化） | 让"权威指南怎么说"可核对 |

不收集：照片、位置、通讯录、任何与营养无关的行为埋点。没有第三方分析 SDK。

## 2. 存在哪、留多久

- **全部数据在自有的 Supabase 项目里**（Postgres）。语料是公共数据，用户数据按 `user_id` 隔离。
- **轨迹保留 90 天**，按月滚动删除（`npm run prune:traces`，默认 dry-run；`docs/rfc/0008` §3.8）。这是个决定而不是默认值：轨迹是餐食与用药的全保真记录，无限期保留等于一个没人负责的默认值。
- **档案与餐食账本保留到用户删除账号**为止 —— 它们是产品功能本身，不是日志。
- 导出轨迹时默认**脱敏**（用户 id 变假名、自由文本替换为长度与哈希），`--with-text` 只用于本地调试。

## 3. 谁能读到

- 用户态（浏览器持有的 JWT）：只能读自己的行，由 RLS 策略在数据库层强制。
- 服务端（service role，仅存在于服务端环境变量）：三处用途 —— 轨迹写入、语料读取、账号删除。写入路径都要求用户态不可写（审计面不能被被审计的主体改写）。
- 运维者：持有 service key，因此**技术上看得到全部数据**。白名单式部署的隐含前提是运维者可信 —— 这一点写在明面上，比含糊不说好。
- 数据库以外**没有副本**：没有数据仓库、没有第三方分析、没有把轨迹导出到别处的定时任务。

## 4. 模型供应商（重要，且不能含糊）

回答生成会把**当轮的上下文**（含用户问题、必要的档案约束、检索到的语料片段）发给模型 API。这意味着：

- **请求内容会离开本项目的服务器**，进入模型供应商的系统。删掉本项目的账号**不会**回溯清除供应商侧的日志或缓存。
- 供应商的公开条款目前是：[DeepSeek Open Platform Terms of Service](https://cdn.deepseek.com/policies/en-US/deepseek-open-platform-terms-of-service.html)（2026-04-29 生效）与 [DeepSeek Privacy Policy](https://cdn.deepseek.com/policies/en-US/deepseek-privacy-policy.html)（2026-02-10 更新）。
  - 平台条款 §5.5 明确：**终端用户数据的处理规则不在供应商隐私政策覆盖范围内**，开发该下游应用的开发者是**控制者**，须自行向终端用户披露 —— 本文即是那份披露。
  - §3.3 要求开发者向终端用户披露个人信息处理规则，并处理访问 / 复制 / 可携带 / 更正 / **删除**与保留相关的请求。因此本项目的账号删除（§5）是条款义务，不是可选功能。
  - §4.2 把 Input 的权利留给你、把 Output 的权利转让给你，并允许把 Input/Output 用于广泛用途（含训练其它模型）。
  - **条款没有对 API 侧的保留期限给出具体承诺，也没有明确声明 API 输入不用于训练。** 消费端隐私政策写明数据存储在中国境内，并对消费端提供"退出用于训练"的权利，但那段政策自述不覆盖 API 的下游终端用户。**本项目因此采取保守立场：把发出去的上下文当作已经离开本项目控制处理，并在 UI 与本文中如实说明，而不是承诺一个条款没有承诺的东西。**
- 若部署改用 OpenAI 兼容网关（本仓库支持 `NUTRIBUDDY_MODEL_PROVIDER` 切换，见 `src/harness/modelAdapter.ts` 的 `PROVIDER_PROFILES`），**该网关的条款同样适用**，运维者必须在切换前把它的条款与保留策略记录进本文（未记录即视为未核对）。

## 5. 删除账号

账号页（`/profile` → Delete account）内的删除入口：身份取自会话，服务端用 service role 删除 `auth.users` 行，其余数据**靠外键级联**（`turns` / `turn_events` 自迁移 0011，`user_profile` / `meal_logs` / `proposals` 自迁移 0016）。删除是**不可逆**的，需要手打 `DELETE` 确认。

删掉的东西：账号、档案（含过敏与用药）、餐食账本、提案、全部轨迹与事件。
**不受影响**：食品目录与依据语料（不是用户数据）。

删掉之后不应该存在的东西，由 `npm run smoke:delete` 用 **service role 计数**验证（不能用被删用户的 JWT 验证——那样必然通过）：五张账号相关表各 0 行，语料表行数不变。

**不会随删除发生的事**：模型供应商侧已经收到的请求内容（见 §4）。若用户的诉求是"供应商也别留"，只能由运维者按供应商的流程另行申请 —— 本文把这条写出来，是因为"删账号 = 全清"是最容易被制造出来的错觉。

## 6. 产品定位：非医疗建议

本项目提供营养信息与记录工具：告诉用户某种食物大致含什么、帮他记录吃了什么、在命中过敏原或用药冲突时拒绝给出建议。

它**不是**医疗器械、不做诊断、不调整用药、不替代医生或注册营养师。模型输出**由 AI 生成，可能出错**（供应商条款 §8.1 同样要求向终端用户明示这一点），涉及医疗、法律、财务的问题不构成任何建议。有疾病、正在服药或怀孕时，请先咨询专业人士。

## 7. 我们不做的

- 不做画像、不做定向广告、不"出售"任何数据（供应商条款同样如此声明）。
- 不用用户数据训练本项目的模型；本项目没有训练流程。
- 不把轨迹用于评测之外的目的；评测产物（`reports/`）只含聚合数字与手写 case，不含用户内容（`docs/rfc/0009` §6）。
