# RFC 0013 — V1.1 检索：切片、融合与注入

> 状态：**Proposed**（2026-09-16）。**V1.1 内容** —— V1.0 的范围见 `docs/rfc/0007`；本 RFC 是 `docs/rfc/0011` 的续篇，只做 V1.0 明确留给 V1.1 的那半边。
> 关联：`docs/adr/0004`（知识 RAG 纳入范围，证据层 only）、`docs/adr/0005`（可引用单元是章节）、`docs/adr/0006`（embedding 自托管）、`docs/rfc/0011`（依据层的 V1.0 部分）、`docs/rfc/0009` §4（报告指标字段）、`docs/privacy.md` §4（新增供应商流向前必须先记录条款）。

## 0. 判据

**规范性建议带可核验引用的比率升上去。**

- 数据来源是 `citationGate` 的**结构结果**（本轮是否有 ≥1 条存活引用、剥离了几条、是否走了 tier-2），不是任何词面正则。
- **营养数字的支撑不进这个比率**：它由 `numericProvenanceGate` 计（ADR 0004 第 2 条不变量）。"数字声明有引用支撑"把两种支撑关系焊在一起，是本 RFC 要拆掉的读法。
- 现行报告里的 `sourceComplianceRate`（`src/eval/summary.ts` 的 `SOURCE_MARKER = /\[source\]|source:|according to|USDA|NIH|ODS/i`）是**文体信号**，只回答"回答里有没有出现这类字样"。`src/eval/metrics.ts` 头部注释把它描述成"数字声明是否有引用支撑"，与实现不符；本 RFC 要求改名降级，并另立结构性的引用支撑率。
- `docs/rfc/0007` D8 原本把"'先扩钉住集还是先上检索'"的仲裁权交给一个覆盖率软指标。§1 的证据表明这个仲裁已经不需要了。

## 1. 为什么现在做检索，而不是扩钉住集

`sources/snapshot.json` 与 `sources/pinned.json` 的实测：

| 事实 | 值 |
| --- | --- |
| 语料规模 | 13 个源、372 段、793,061 字符 |
| 钉住集 | 29 段 = **7.8%**，字符预算 **23862 / 24000（99.4%）** |
| 被配额或预算挤掉的段落 | **55 段**（含 `ods-magnesium#...-diuretics`、`ods-iron#...-levodopa`、`ods-vitamin-k#...-antibiotics`） |
| 零覆盖的源 | `ods-vitamin-d`（44 段）、`ods-zinc`（30）、`ods-vitamin-c`（25）、`dga-2020-2025`（8）全部 pinned = 0 |

钉住集不是按问题相关性挑的，是按优先级配额凑的（0 药物相互作用 8 / 1 用药相互作用 5 / 2 推荐摄入量 8 / 3 食物来源 8 / 4 过量风险 3）。问"维生素 D 该吃多少"时上下文里恰好一段维生素 D 都没有；问"镁和利尿剂"时那一段正在 `excludedByBudget` 里。

**扩钉住集撞的是双重天花板**（`PINNED_MAX_SECTIONS=40` 与 `PINNED_MAX_CHARS=24000`），最多到 10.8% 覆盖，且这 6k token 是每轮常驻成本。检索是把这份成本从"每轮常驻"变成"按需"的唯一办法。

## 2. 决定一览

| # | 决定 | 依据 |
| --- | --- | --- |
| D1 | 检索只决定**哪些章节可用**；不提供数字、实体、写入，不参与安全判定 | ADR 0004 |
| D2 | 判据是引用支撑率（§0），数字仍归 provenance gate | §0 |
| D3 | 钉住段留在 pinned region，检索命中进**新的 dynamic 槽位** | 保住 system 消息的字节稳定与缓存前缀 |
| D4 | 单元是章节内的 **chunk**（段落优先 → 尺寸上限 → 尺寸砍开处重叠） | §3 |
| D5 | 引用仍指向**章节**；chunk 只在索引里 | ADR 0005 |
| D6 | 命中注入：短章节整段，长章节才用窗口 | §5 |
| D7 | 书目段在**摄入层**排除并留痕 | §3 |
| D8 | 词法 + 向量 + RRF 一次到位，**rerank 延后** | §4 |
| D9 | embedding = Supabase `gte-small` 384 维 | ADR 0006 |
| D10 | **每轮无条件检索**，检索上限计入最坏成本 | §5 |
| D11 | 评测：引用支撑率 + `retrieval_miss` 归因 + 最小 `rag_boundary` 断言；**不做 Recall@k/MRR** | §6 |

## 3. 切片

**规则**（边界优先级从高到低）：

1. 段落（`\n\n`）是最小尊重单位，绝不跨段缝合；
2. 段落自身超过上限时降级到句子边界；
3. 仍超过上限则硬切。

参数：目标 800–1200 字符，硬上限 **1600**，被尺寸砍开处给 **15%**（≈150 字符）重叠。

**重叠必须计入上限**：在真实语料上按"重叠另计"跑一遍，954 个 chunk 里有 11 个突破 1600——上限漏在重叠上。

**实测**（372 段的全量结果）：954 个 chunk，尺寸中位 **932**、p90 1168、平均 834 字符。段落结构真实存在（108 个长段的段落数中位 5、p90 64），但纯按段落切会剩下 26 个段内超过 1200 字符的胖段，所以尺寸界限不能省。

**标题前缀**：每个 chunk 的索引文本前拼 `heading`（+ `sectionPath`）。不拼的话，`ods-calcium#calcium` 那种以"This is a fact sheet intended for health professionals…"开头的段，检索时什么都匹配不上。

**书目排除**：`*-references` 是 12 段、267,581 字符 = 语料的 33.7%，切出来是 **251 个 chunk = 26.3% 的索引**。书目是指向证据的指针，没有可引用的主张；留在索引里，词法侧会命中作者名与期刊名，向量侧会把它当同主题，两头都在挤掉正文。因此**在摄入层**给 section 打 kind 标记并排除（不是检索时打补丁——"这段是书目"是关于语料的事实，不是关于查询的事实），并在 `sources/snapshot.json` 里点名排除了几段几 chunk（沿用 `excludedByBudget` "不静默丢弃"的先例）。

**chunk 身份**：`sectionId#c<ordinal>`，只存在于索引。不是可引用单元（ADR 0005）。

## 4. 索引与融合

- **迁移**：`create extension if not exists vector with schema extensions;`、chunk 级索引行（或 `source_sections` 上的列）、`tsvector` 列 + GIN、`embedding extensions.vector(384)` + HNSW、以及逐表的授权与 RLS 收口（对齐 0013/0014 的先例，新表默认 `revoke` 后按需 `grant`）。
- **词法侧**：`tsvector` + heading 加权，负责条款号、剂量、上限这类精确串。**原生 `ts_rank` 不是 BM25**（只看单文档、缺全局语料统计）；出现排序质量不足时先考虑 `pg_search` 类扩展，而不是更换检索引擎（ADR 0004 §6）。
- **向量侧**：`gte-small` 384 维（ADR 0006）。
- **融合**：RRF，`k = 60`，取 **top-5**，按**父章节去重**（同一章节只出现一次，取它分最高的 chunk）。
  **融合写在 TypeScript 里，不是 SQL 的 CTE（对 §4 初稿的偏离，实现于 #134）**：SQL 只提供两个 TS 表达不了的排序原语（`ts_rank` 与 `<=>` 距离算子，迁移 0018 的两个函数），融合由 `src/evidence/retrieval.ts` 一份实现承担。理由是**同一排序规则只能有一份实现**——CI 跑的 in-memory 检索器与生产跑的 Postgres 检索器必须给出同样的顺序，而两处各写一遍 RRF 正是"这个一致性悄悄不再成立"的方式。章节得分取**该章节最好 chunk** 的分数而不是求和：求和会让 chunk 多的章节压过真正回答问题的章节，那是 43k 字符的参考文献段本会赢下排序的另一面（§3 已从另一头排除了它）。
- **rerank 延后**：它是第三个模型调用与一层新的延迟/成本，触发条件是"top-5 精度不足到影响判据"。到那时再加，而不是现在预防性地加。

## 5. 注入与预算

**位置**：钉住段继续留在 system 消息（`assemblePinnedRegion` 的 `evidence`），检索命中走 `assembleContext` 的**新槽位**，插在 history 之后、当轮 user 输入之前。

理由：`contextAssembler.ts` 第 53–59 行给钉住证据的位置写了理由——"按 sectionId 排序、跨轮字节稳定，因此能吃 prompt cache"。**这句话的前提是"证据集跨轮不变"，而检索命中按定义就是按问题变的。** 拆成两块而不是把全部证据挪进 dynamic，是为了不牺牲那 6k token 的缓存前缀；插在 history 之后，是为了不截断 system + history 的共享前缀。

**注入范围**：命中 chunk 所属章节 ≤2000 字符时注入**整章**；超过时只注入命中窗口（+ 相邻 chunk）。中位数章节是 1065 字符，所以常见情形下"注入的文本 = 被引的章节"，引用与模型看到的文本完全一致。

**上限与成本**：top-5 × 1600 字符 = 8000 字符 ≈ **4,000 token**，作为常量计入 `src/lib/turnCostEstimate.ts` 的 `base`——与 S4 的 evidence 块同构（它也是这样按上限计的，见该文件第 57–74 行的理由："a bound that only holds at the corpus size of the day is not a bound"）。

flash 档 cache-miss $0.28/Mtok、`MAX_STEPS = 8`、检索块在每一步都被重发 → **最坏单轮 +$0.009**（8 × 4000 token）；对照日配额 `QUOTA_DAILY_COST_USD = 1`、40 轮/天，最坏 +$0.36/天。步内前缀可命中缓存（$0.028/Mtok）时实际约 $0.001–0.002/轮。

**触发**：每轮无条件检索。任何"是否需要依据"的条件判定都可能漏掉本该有依据的轮次，而这类漏判在报告里长得像"检索召不回"，会污染归因。代价是简单查询（"100g 鸡胸多少蛋白"）也固定多花这 4,000 token。

**降级（fail-closed）**：检索不可用或命中低于阈值时不注入，答案退化为"无引用 + 明确说明依据不足"，**绝不允许以模型记忆补位**（ADR 0004 第 4 条）。

**检索来源留痕**：哪些 chunk 命中、来自词法侧还是向量侧，要进事件流。否则重放无法复原当轮证据集是怎么来的。

## 6. 评测

- **接线**：`HarnessResult`（`src/eval/types.ts`）目前没有任何引用字段——`citationGate` 已经产出 `passed` / `kept` / `stripped` / `reasons`，且 tier-1（剥离、不进重生成预算）与 tier-2（声称有据却无引用 → 重生成 → 拒答）在 verdict 上已用 `terminal` 分开。评测要消费的是这些结构结果。
- **报告**：新增一节报"引用支撑率"，分母是**应有依据**的 case（不是全部 29 条）。`retrieval` 这个字段目前在 `src/eval/summary.ts` 是占位（"V1.1; the field exists, the value does not"），按本节口径落地或删掉，不留第三种含义。
- **数据集**：补若干"应有依据"的 case（例如维生素 D、锌这类当前零覆盖的源）。现有 29 条几乎都是 catalog 型问题，分母里可能根本没有几条需要引用。**n=29 < 30 的报告纪律不变**（`MEANINGFUL_SAMPLE_SIZE`）。
- **归因**：失败分桶加 `retrieval_miss`（ADR 0004 后果 §"评测与自进化"已经点名）。
- **`rag_boundary` 最小断言**：检索不可用时不得以记忆补位、检索到的文本不得把数字偷渡进答案。
- **不做 Recall@k / MRR**：它们需要"每条 query 对应哪些章节才算命中"的人工标注集，而语料刚落过地改动（书目排除 + chunk 化）；没标注的 Recall@k 是自出考卷。D8 原本设计的"人工抽查 N 条真实问题"当**软指标**，与 D8 的口径一致。

## 7. 切片顺序与依赖

| 切片 | 内容 | 依赖 | 验收 |
| --- | --- | --- | --- |
| **T1** | 迁移（vector 扩展、chunk 索引行、tsvector + GIN、vector(384) + HNSW、逐表授权/RLS）+ `EmbeddingPort` / `RetrieverPort` 骨架与 stub | — | `bash scripts/verify-migrations.sh` 退出码 0；无网络时端口可 stub |
| **T2** | 切片规则 + 书目排除（section kind + `snapshot.json` 留痕）+ 语料侧 embedding 生成 | T1 | 摄入后 chunk 数与排除数可断言；重复摄入幂等 |
| **T3** | 词法召回（tsvector + heading 加权） | T2 | 固定语料 fixture 上的 top-5 离线断言 |
| **T4** | 向量召回（Edge Function + HNSW） | T2 | 同一段文本两侧向量的对拍记录 |
| **T5** | RRF 融合（k=60）+ 父章节去重 | T3, T4 | 融合顺序的确定性断言 |
| **T6** | dynamic 槽位注入 + 短段整段/长段窗口 + 上限常量计入 `turnCostEstimate` | T5 | 预算断言；缓存前缀形状断言（system 消息字节不变） |
| **T7** | 评测接线 + 报告小节 + 数据集补 case | T6 | 判据可读：引用支撑率进报告 |
| **T8** | `retrieval_miss` 归因桶 + `rag_boundary` 最小断言 | T7 | 检索不可用时的降级路径被断言 |

T3 与 T4 可并行。T2 之后每一步都能单独回滚（T3/T4/T5 各自在端口后面）。

## 8. 风险

| 风险 | 触发信号 | 处置 |
| --- | --- | --- |
| `gte-small` 召回质量不足 | 引用支撑率不升，而 `retrieval_miss` 集中在语义型问题 | 换 embedding 模型 = 一次迁移（384 维）+ 重跑摄入；摄入按 `content_hash` 幂等 |
| 词法排序弱（`ts_rank` 非 BM25） | 精确串被长章节挤掉 | 先试 `pg_search` 类扩展，不换引擎（ADR 0004 §6） |
| chunk 把语义切碎 | 命中窗口缺条件句，答案与引用不符 | 调尺寸/重叠；极端情况回落到整章注入 |
| 检索块破坏缓存前缀 | `cacheHitRate` 掉、$/turn 上升 | 槽位位置固定在 history 之后；用 T6 的前缀形状断言守住 |
| 检索把无关段落塞进上下文 | 引用存活但引用错了段落 | 这是 `retrieval_miss` 之外的新桶（引用正确率），进 T8 的归因，先记账不加机制 |

## 9. 明确不做

- 不做 Recall@k / MRR 与人工相关性标注集（§6）。
- 不做 rerank（§4）。
- 不做检索 subagent：ADR 0004 §7 是条件式授权（"仅当出现多轮检索 + 覆盖判停"），当前没有该场景。
- **不收缩钉住集**：撤销是可逆的（数据而已），但要先有检索质量数据才能判断能不能撤掉那 29 段承担的下限保证。RFC 0011 定义的 required 三段（warfarin / 保钾利尿剂 / levothyroxine）继续留在 pinned。
- 不做按用户相关性挑证据（那本质是检索，属本 RFC 而不是用户层）。
- 不让检索结果参与任何安全判定、不把语料当数字来源（ADR 0004 §2）。

## 10. 与 issue tracker 的衔接

沿用 `docs/rfc/0007` §6 的约定：**一份 spec 的 ticket 小节就是一组 issue 的草稿**，转 issue 时带上 RFC 编号、切片号与验收项编号（如 `RFC 0013 §7 / T3`），使每个 issue 都能回答"为什么做"和"怎么算做完"。本 RFC 不复制 issue 列表。

本 RFC 之外、已被它暴露出来的两笔账（不属于检索本身）：

1. `docs/privacy.md` §4 未闭合：默认 provider 已是 commandcode 网关，而 §4 只记录了 DeepSeek 的条款，按 §4 自己的规矩"未记录即视为未核对"。归 #113 的部署前置。
2. `docs/rfc/0007` / `0008` / `0011` 的状态头仍写 `Proposed`，而它们已经落地（`AGENTS.md` 的 Next 列表逐条说明已收口），`AGENTS.md` 还在复述这个过期状态。违反本文档体系自己的 doc lifecycle。
