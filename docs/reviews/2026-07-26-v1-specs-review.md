## 阻断

### 1. `docs/rfc/0008-trace-persistence-and-replay.md` §3(6) / §6 / §7 → 批量缓冲策略与"不丢不重"+"无缺口"三个承诺互斥

**问题**：§6 允许两种 flush 策略（"每 turn 一次 flush **或**按 N 条"），但两种策略各自单独就与另外两条约束冲突：
- 若"每 turn 一次 flush"（turn 结束才落库）：turn **运行期间**（用户最可能刷新/断网的窗口）Postgres 里没有该 turn 的任何事件，`GET /api/turns/:id/events` 在这个窗口返回空——这正是 §5/D4"会话中断（刷新/断网）后凭 turnId+lastSeq 看到已产生事件"要解决的场景，此时反而失败。
- 若"按 N 条 flush"：§3(6)"中间事件写失败不阻塞 turn"意味着某条事件可能写失败但后续事件继续写、continue，`listByTurn` 就会出现 seq 缺口，与 §7 测试表"seq 连续性：listByTurn 返回的 seq 严格递增且无缺口"直接矛盾。

**改法**：二选一并把决定写进 §6，不要把两种策略并列成"或"：
- 方案 A（推荐）：改为"每条事件写后立即 append，不做批量"，牺牲一点写放大换取重放正确性与无缺口保证同时成立（事件数每 turn 仅 4–30 条，§6 自己的估算已经说明批量收益很小）。
- 方案 B：保留批量但把 §7 的断言改成"seq 允许非连续，客户端按 seq 排序、允许跳号"，同时把 D4 的验收范围明确限定为"turn 已结束"的断线场景，不承诺 turn 进行中的实时重放。

这是 S1（backlog 定性的"头号阻塞项"）自身尚未拍板的设计矛盾，必须在写 `SupabaseTraceStore`（#88）之前解决，否则 T3/T5 会做到一半返工。

## 应修

### 2. `docs/rfc/0006-cloud-runtime-architecture.md` §9 → 文档内部自相矛盾，残留已被自己更正的旧数字

§9"迁移触发条件"仍写"撞上 **60s** 函数上限"，但同一份文档 §2 与 §12.1 已明确指出这个 60s 是 ADR 0002 记录时的过期前提，现行边界是 Hobby 300s / Pro 800s。§9 没有跟着改。

**改法**：把 §9 该句改为"撞上函数时长上限（Hobby 300s / Pro 800s，见 §12.1）或 catalog 冷启动成本"。

### 3. `docs/adr/0002-delivery-surface-cloud-hosted-pwa.md` §上线门槛 vs issue #113 / #119 → 与 Accepted ADR 直接矛盾

ADR 0002（Accepted）明确把"模型账号设消费上限""敏感变量只勾 Production""build 后验证无密钥泄露"列为"运维侧（人工执行，**不进 issue tracker**）"，理由是"这是部署决定的边界条件，不是一次性任务"。但 backlog 把这三条原样做成了 issue（#119 全部对应第 1 条；#113 范围里逐字包含第 2、3 条）。ADR 排位高于 RFC/backlog（`AGENTS.md` 权威顺序），RFC/backlog 改变了 ADR 的决定却没有回写 ADR 做同步说明。

**改法**：二选一：(a) 关闭 #119，把第 2/3 条从 #113 范围里移出，按 ADR 0002 原意留在运维清单而非 issue；或 (b) 更新 ADR 0002 该节文字，承认"作为一次性上线检查项仍建 issue，但要求上线后转为常驻运维清单，不能被'关闭'掉就当长期失效"。两者选一即可，当前是两份文档各说各话。

### 4. `supabase/migrations/0005_rls_policies.sql`（既有表）vs `docs/rfc/0006-cloud-runtime-architecture.md` §7 → 生产实践要求只套在新表，老表敞口和性能隐患未被任何 ticket 回填

RFC 0006 §7 给出两条"生产实践要求"：① 开 RLS 同时必须 `revoke` 默认给 `anon`/`authenticated` 的 grant；② 策略列用 `(select auth.uid())` 写法触发 initPlan 缓存。RFC 0008 §4（`turns`/`turn_events`）与 RFC 0011 §3.1（`sources`/`source_sections`）都对**新表**照做了。但现有 `proposals`/`meal_logs`/`user_profile`（`0005_rls_policies.sql`）三张表：没有任何 `revoke`，策略写法是裸 `auth.uid() = user_id`，不是 `(select auth.uid())`。34 个 issue 里没有一个覆盖"回填老表的 revoke + 索引写法"。RFC 0006 §7 自己引用的 Supabase 官方实测（10 万行表上 171ms → <0.1ms）证明这不是装饰性建议。

**改法**：在 S1 或 S5 新增一个 ticket："迁移 0014：为 `proposals`/`meal_logs`/`user_profile` revoke 默认 grant + 策略列改写为 `(select auth.uid())`"，跑一遍现有测试确认策略语义不变。不需要新建表，只是一条修订迁移。

### 5. 健康数据隐私：全保真轨迹落库却无保留策略，V1.0 验收不要求解决它

RFC 0008 §12 未决项 1 把"payload 是否全保真"（含餐食/用药）标记为未决，"建议：全保真 + 保留策略（如 90 天）+ 导出时脱敏"——但这只是建议，不是决定。RFC 0007 §2 的 D3/D9 验收条件只要求"能查出全部事件"和"他人 JWT 读不到"，不要求保留策略已定。结果是：V1.0 上线时，餐食+用药会被全保真、无过期时间地写进 Postgres，唯一的删除路径是用户主动删账号（#115），没有默认保留期，也没有导出脱敏。这是明确的个人健康数据处理决定，不应该以"未决"状态带着上线。

**改法**：在 `docs/rfc/0008` 把未决项 1 提升为决定，至少定一个默认值（例如"V1.0 默认无限期保留，S1.1 前必须加 90 天滚动清理"），并在 #115（隐私说明）里显式写出这个默认值，不要只写"保留多久"这种占位描述。

### 6. 隐私说明遗漏第三方模型供应商的数据留存 — `docs/rfc/0007` §4 / issue #115

餐食与用药以自然语言进入 prompt，发给 DeepSeek/Claude 等模型 API。RFC 0006/0007/0008 的隐私相关文字通篇只谈 NutriBuddy 自己数据库的删除级联，完全没提模型供应商侧对请求内容的留存/训练使用政策。用户删了 NutriBuddy 账号，不代表供应商侧的请求日志同步清除——这是"账号删除=级联删轨迹"这句话制造的错觉。

**改法**：#115 范围里加一条"查证并写明所用模型 API 的数据留存/是否用于训练的条款链接"，作为隐私说明的必要组成部分，而不是只描述自己数据库内的删除路径。

### 7. issue #115 标签与 DoD 不符：`documentation` 标签下藏着一个代码库里目前完全不存在的功能

#115 的完成定义是"删除路径实测可用（删账号后查不到用户数据）"，但全仓库没有任何 `deleteUser`/账号删除相关代码（已核实：`app/`、`src/` 下无匹配）。这意味着 #115 隐含"新建一个调用 Supabase Admin API 删除 `auth.users` 的服务端端点或脚本"——这是代码工作，不是文档工作。对照 #101（同样是"脚本 + 人工执行"的组合）正确带了 `enhancement` 标签，#115 只带 `documentation, ready-for-human`，会让按标签路由的 agent 直接跳过它认为"只是写文案"的这张票。

**改法**：给 #115 加 `enhancement` 标签，或者拆成两张票：一张 `documentation`（隐私文案 + 非医疗建议定位），一张 `enhancement`（账号删除端点/脚本 + 实测）。

### 8. S3 的单轮最坏成本预估公式引用了 S4 才产出的"证据子集"，但 S3 不依赖 S4

`docs/rfc/0010-cost-quota-and-allowlist.md` §3.3："单轮最坏成本预估：用 pinned region + 目录签名 + **证据子集**的 token 上界 × 单价估算"——这里的"证据子集"就是 RFC 0011 §3.7 的钉住证据集（S4 产出，issue #111）。但 `docs/rfc/0007-v1-release-plan.md` §3 的依赖表里，S3 只依赖 S1，不依赖 S4；S3 和 S4 是并行分支。如果 S3（#100）先落地，公式里的"证据子集"项无实际数据可用，要么临时按 0 估算（成本上界偏低，正是 RFC 0010 想防的"单轮异常"漏防）、要么等 S4 落地后再返工——这两种情况 backlog 都没有体现。

**改法**：在 #100 的范围里显式加一句"证据子集項在 #111 落地前按 0 计入，#111 完成后需回头补一次预估校准"，或者干脆把 #100 的依赖改成"S1（必须）+ S4（若已存在则纳入计算，否则占位）"，让这个二次修改点在 backlog 里可见。

### 9. `citationGate` 的失败处理复用了 C1 级安全闸的终态，与 ADR 0004 自己的风险定性不一致

ADR 0004 明确"知识 RAG 没有安全属性依赖它""这是最低风险的引入方式"。但 RFC 0011 §3.5/§3.6 让引用校验失败走"追加反馈重生成（最多两次）→ 确定性拒答"——与 entity/numeric/advisory 三个**安全**闸完全同一终态。后果：一个营养事实、过敏原判断都正确的回答，仅因为引用的一句"膳食指南建议…"没能通过章节版本校验，就会被整体拒答。这把"依据层"的失败严重度悄悄拔高到了和"过敏原冲突"同一级，与 ADD 的 C1（"一个错误的过敏原或药物冲突答案会伤人；拒绝只是惹恼"）论证的初衷——拒绝是为规避真实伤害而付出的代价——不匹配：这里没有伤害风险，只有"这句话没有出处"。

**改法**：citationGate 违规时的降级路径改为"剥离未通过校验的引用及其依赖的断言句，保留答案主体"，而不是整体重生成/拒答；只有在词面兜底（§3.6，断言了权威依据却完全没给引用）时才触发现有的重生成/拒答机制。

## 建议

### 10. `docs/rfc/0008` §4 迁移 → `turn_events_turn_idx` 是冗余索引

`turn_events` 主键已是 `(turn_id, seq)`，Postgres 会为主键自动建同列同序的唯一索引；紧接着又显式 `create index turn_events_turn_idx on public.turn_events (turn_id, seq)`，与主键索引完全重复，只增加写放大、不提供额外查询收益。

**改法**：删掉这条 `create index`，查询直接吃主键索引。

### 11. `docs/rfc/0010-cost-quota-and-allowlist.md` §9.3 → "并发轻微超发可接受"应从未决提升为决定

§9 未决第 3 条只写"建议接受"，但 issue #97 的正文已经把它当作既定事实描述（"配额是软上限……并发轻微超发可接受"）。规范正文和 backlog 口径不一致，虽然结论本身合理（不做分布式锁的取舍成立），但应该把这句话从"未决"移进 §3.3"决定"，避免以后有人对着 §9 的"建议"质疑 #97 的实现依据。

### 12. `docs/rfc/0006-cloud-runtime-architecture.md` §8 → V1.1 内容占了 V1.0 RFC 近一半篇幅

§8（Skill / 场景注册表）连同 §8.1–§8.4 共约 115 行，但 §10 落地顺序把它排在 step 6，明确是 V1.1 范畴，且不被本批任何 S1–S5 ticket 引用。放在一份标题为"云端运行架构（V1 上线形态）"的 RFC 里，加大了这次评审和未来读者理解 V1.0 实际范围的成本。

**改法**：把 §8 整节拆到一个独立的 V1.1 RFC（如"场景策略包设计"），0006 只保留一句指针。不改变任何决定内容，只是搬家。

### 13. `docs/rfc/0007-v1-release-plan.md` §2 D8 → 验收门槛与 ADR 0004 的产品目标不对称

D8 只要求"一次带依据的回答中引用可核验"即通过。ADR 0004 的立项理由是"用户要的不是一个会算数的记录器，而是一个能给出依据的顾问"——但只验证"能力存在"（跑通一次）不代表"日常够用"。40 段钉住证据集是与用户无关的通用集，多数具体问题可能命中不到，D8 目前对此没有任何覆盖率要求。

**改法**：给 D8 加一条软指标（不进 fail-closed 逻辑，只进 eval report）：抽样 N 条典型问题，统计命中钉住证据集产出可用引用的比例，写进 `eval:report` 的 `retrieval`/`rag_boundary` 类别（RFC 0009 §4 已经为检索类指标留了字段），作为 V1.1 是否需要提前扩容钉住集或提前上检索的判断依据。

## 覆盖说明（六类逐项）

1. **冲突/残留表述**：见阻断 #1（间接）、应修 #2、#3。ADD §Out of Scope / §Phases 与 ADR 0004 的同步已被 #104 正确前置为 S4 首票，未发现遗漏。
2. **安全论证**：见应修 #4（RLS/grant）、#9（fail-closed 严重度错配）。数字来源、实体铸造、写入路径三条不变量在本批 RFC 里未见削弱。
3. **内部自相矛盾/不可行**：见阻断 #1、应修 #8、建议 #10。SCHEMA_VERSION 迁移（1.9.0→1.10.0）与 golden 迁移路径（issue #108）设计自洽，未发现问题。
4. **过度设计**：见建议 #12。整体克制，多处已自带"不需要就不建"的收敛条件（如 RFC 0010 §4 的 `usage_limits` 空迁移选项），V1.0 范围本身没有明显可删的机制。
5. **缺失的决定/未列风险**：见应修 #5、#6；建议 #11、#13。钉住证据集与 V1.1 检索的关系（RFC 0011 §3.7/§8）已有明确、自洽的分期决定，未发现缺口。
6. **backlog 与 spec 不一致**：见应修 #7、#8。34 个 issue 与 RFC 0008–0011 的 ticket 计数逐一核对（6+5+7+8+1+7=34）无缺票、无重复；依赖字段抽查未见错标（除 #8 指出的隐性缺失依赖）。label 体系（`ready-for-agent`/`ready-for-human`）与 `docs/agents/triage-labels.md` 定义一致，仅 #115 一处用错（见应修 #7）。

## Top 3 必须修的项

1. **阻断 #1** —— RFC 0008 的批量缓冲策略与"断线不丢不重"+"seq 无缺口"两个承诺互斥，S1 是公认的头号阻塞项，这个矛盾不解决，S1 做到一半必然返工。
2. **应修 #5 + #6** —— 健康数据（餐食+用药）全保真入库无保留策略、隐私说明未覆盖第三方模型供应商留存，这两条合起来是 V1.0 上线前唯一真正"没有决定"的隐私风险，且没有 owner。
3. **应修 #4** —— 现有三张业务表的 RLS grant/写法没有回填 RFC 0006 §7 自己定的生产标准，是当前唯一"知道问题所在、却没人接的" 安全卫生债务。

**总体判断**：这套 spec 的分层设计（seam 不动、持久化旁路、闸不增加新形状、V1.0/V1.1 分期）是自洽且克制的，backlog 与六份 RFC 的 ticket 对应关系严密，可以立即开工 S2/S3/S5 的大部分票。但 S1（一切的前置）自身带着一个尚未拍板的设计矛盾（阻断 #1），不建议在这条矛盾解决前开始 `SupabaseTraceStore` 的实现；把阻断 #1 和应修 #4、#5、#6 处理掉之后，这套 spec 足以开工。

## 复审结论（2026-07-26）

### 阻断 #1 — 部分解决

flush 策略矛盾本身**已解决**：逐条 await 写入成功后再推客户端、不批量、写失败重试一次后以 `crash`（既有 `StopReason`，未新造）终态收尾，`docs/rfc/0008` §3(6)/§6/§7/§10/§11 五处已同步改写，D4 与"seq 无缺口"不再互斥，自洽。

**残留**：改法本身引入了一个未被承认的新代价——把同步 Postgres round-trip 塞进了每一个 `step`/`model_call`/`gate_verdict` 事件推给客户端之前的路径上，而这条路径正是 ADD 设计"step 事件流"用来 masking latency 的关键路径。§6"容量与性能"只讨论了写放大（存储量），没有讨论这一 round-trip 对响应速度的影响；`docs/rfc/0006` §5 的单 turn wall-clock 预算、`docs/rfc/0009` §4 的 P50/P95 延迟口径也都没有把"轨迹写入延迟"从"模型延迟"里拆出来。不是逻辑矛盾，是遗漏了一个需要量化的性能假设。

**改法**：在 `docs/rfc/0008` §6 补一句量化预期（同区域 Supabase insert 的典型延迟、30 事件 worst case 的总增量，并确认仍在 wall-clock 预算内）；在 `docs/rfc/0009` §4 的延迟指标表加一行 `trace_write_latency_ms`，让"turn 变慢"以后能分清是模型慢还是 DB 慢。**不阻塞 S1 开工**——现有 300s 预算下这条路径大概率安全，只是需要补一条可验证的假设。

### 应修 #8 — 部分解决

### 应修 #9 — 部分解决

方向性决定**已解决且自洽**：ADR 0004 决定 3 与 `docs/rfc/0011` §3.5 的分级处置（tier-1 校验失败→确定性剥离、不拒答；tier-2 断言无引用→走既有重生成/拒答）两处文本一致，且这个设计本身与"gate 是纯函数"不冲突——剥离是"根据输入产出一个新的 `TypedOutput` + verdict"，仍是无副作用的确定性变换，不违反纯函数约束。

**残留，两处未同步 + 一处语义空缺**：

1. `docs/rfc/0011` §6 DoD 仍写"引用未知/失效章节必被闸拦下并触发重生成或拒答"——这句是旧的"一刀切"表述，与 §3.5 新定的"tier-1 不重生成、不拒答"直接矛盾，DoD 没跟着改。
2. §7 ticket T5 仍写"citationGate.ts（四条件 + fail-closed）+ verdict 事件 + **反馈重生成接线**"——"反馈重生成接线"这个措辞对应的还是统一走重生成的旧行为，没有反映"只有 tier-2 才接反馈重生成"这个新分工，容易让实现者把 tier-1 也接进 `turn.ts` 里那个"share one regenerate budget"的既有共享预算（已在 `turn.ts:440` 附近验证存在）。
3. 语义空缺：tier-1 剥离复用了与entity/numeric/advisory 三个安全闸相同的 `verdict: "block"` 取值，但下游行为完全不同（不计入 regenerate 预算、不影响终态）。ADD 的纪律是"scorer 看不到的行为不存在"——现在 scorer/trace 读者要靠"这条 verdict 的 `checkName` 恰好是 `citation_provenance`"这种隐式约定才能知道这次 `block` 不会触发 turn 级别的后果，而不是从事件本身的字段直接读出。

**改法**：① 把 §6 DoD 与 §7 T5 的措辞同步成 §3.5 的分级表述；② 给 `gate_verdict` 事件加一个显式字段区分"计入 regenerate 预算的 block"与"仅剥离、不计入预算的 block"（例如 `terminal: boolean` 或等价机制），不要把这个区分只留在 checkName 的阅读约定里。**不阻塞 S1**（citationGate 属 S4），但应在 S4 排期前处理，否则 T5 的实现者大概率会按 ticket 原文把 tier-1 也接进重生成循环，做出来的行为会和 §3.5 的决定不一致。
