# 菜谱分解与「中文菜系覆盖」的边界

> 2026-07-23。澄清 `docs/ADD.md:135` 的 never 非目标边界，并固定一条不变量。
> 本 ADR 不新增能力，只划清已有非目标的适用范围。

`docs/ADD.md:135` 把 **Chinese cuisine coverage** 列为 never 非目标。但产品要能记录中餐（dogfooding 阶段的唯一用户吃中餐），二者看似冲突。本 ADR 判定：不冲突，因为两者指的不是同一件事。

## 决定

- **never 挡的是「项目去策展中餐营养数据库」** —— 即由项目维护一份中式菜品的营养事实表。这是无底洞：菜品无穷、做法各异、无权威数据源，且每条数据都需要审核才能进入推荐面。
- **菜谱分解不在 never 范围内。** 它是通用机制：把复合菜品拆解为基础食材引用 + 克数，营养由代码从既有 catalog 计算。意面与宫保鸡丁走同一条路径，机制文化中立。
- **不变量：菜谱永远不携带营养数字。** 菜谱只携带配料引用（catalog food id）+ 克数 + 成菜重量。任何营养值都是从 catalog 事实计算得出，不由模型提供、不由用户手填、不从外部抄录。
- **本 ADR 不打开 Phase 5。** 菜谱分解不需要 knowledge RAG、不需要 web search、不需要新的 observation 源。`docs/adr/0001` 的检索 subagent 仍然 metric-gated，闸保持关闭。
- **自建食物是逃生舱，不是覆盖手段。** 仅服务拆不到基础食材的包装食品（手录营养标签）。它不构成「中餐覆盖」，因为它不预置任何菜品数据 —— 每条都由用户为自己创建。

## 为什么（权衡）

放弃「把中餐支持当作数据覆盖问题」，因为：

1. **它把无界问题伪装成有界问题** —— 策展菜品数据库没有终点，而基础食材是有界集合。分解把无穷的菜品映射到有限的食材，问题规模从 O(菜品) 降到 O(食材)。
2. **数据权威性** —— 中式菜品没有 USDA 级别的权威营养源，任何策展结果都是估算。而基础食材有 USDA 实测数据，分解后的计算结果继承这份权威性。
3. **它会诱导架构违规** —— 若把中餐当覆盖问题，唯一出路是让模型或外部检索提供菜品营养数字，直接违反「facts / numbers 由确定性代码定义」，并需要跳过 Phase 5 的指标闸。分解路径不需要任何一项妥协。

保留 never 那条不变，因为它挡住的正是上述第 3 条的滑坡。

## 后果

- 模型在菜谱路径上的职责是**提议组成结构**（哪些配料、各多少克），与它在 `log_meal` 上已有的职责同构 —— 提议实体与数量，由 resolver 铸造 food id，由代码计算营养。
- `numericProvenanceGate` 无需改动：菜谱营养源自 catalog observation，天然可溯源。
- catalog 需覆盖基础食材（含油脂、调味料等烹饪投入）才能让分解结果准确。这是 snapshot ingestion 的范围，不是本 ADR 的决策。
- 具体设计见 `docs/rfc/0005-recipe-decomposition-and-custom-foods.md`。
